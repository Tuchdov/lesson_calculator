# Design: Grow payment links in the WhatsApp payment message

Generated by /office-hours on 2026-08-24
Reviewed by /plan-eng-review on 2026-08-24
Branch: grow-payment-link-integration
Repo: lesson_calculator
Status: APPROVED
Mode: Builder

## Problem Statement

The month-end WhatsApp message tells each student their lesson count and total, then
says `[קישור לתשלום]` ("payment link") as literal dead text
(`src/lib/whatsapp.js:19`). There is no link. The student reads what they owe and pays
by some other route.

Replace that placeholder with a real Grow payment link, minted per student for that
student's exact amount, delivered inside the existing Hebrew message.

## What Makes This Cool

The placeholder has been sitting in the template waiting for this. The whole feature is
filling in one token that was designed for it from the start.

One button prepares every link for the month in a single pass, so the whole collection
run is set up before the first message goes out and each send click stays instant.

## Constraints

- Single user (the teacher's own Google account). 30-35 students.
- Desktop only. WhatsApp is used on the computer.
- Grow sandbox until a real link round-trips successfully.
- Make bills per **module execution**, so Webhook + Grow + Response is ~3 operations per
  student, roughly 105/month against a 1000/month free tier.
- Tests are pure-function only (`deno test`), importing only from `src/lib/` and
  `src/api/`. Logic that needs coverage must live there.

## Data Flow

```
  Calculator table                         Vercel                    Make            Grow
  ───────────────                          ──────                    ────            ────
  [Prepare all links]  ──6 at a time──>  /api/create-payment-link
                                            │
                                            ├─ verify Google token ──> tokeninfo
                                            │    email == ALLOWED_EMAIL?
                                            │    aud   == our client id?
                                            │    not expired?
                                            │
                                            └─ POST ─────────────────> webhook ──> Create
                                                                          │        Payment
                                            <──────── { link } ───────────┘        Link
                                            │
     each row stores {link, amount} ───> vocalCalc:paymentLinks:<hash>
     as it arrives (crash-safe)              key = {month}:{student}

  [שלח] on a row
     │
     ├─ stored link AND amount unchanged ──> open wa.me immediately (1 click)
     └─ no link, or amount changed ────────> mint, then open (2 clicks)
```

## Premises

1. **A Vercel serverless function is added, reversing `DESIGN.md`'s "No Node.js backend
   server" constraint.** Accepted deliberately, scoped to secret-holding proxies only.
   User's words: "Its ok that the project will grow to backend this is graudal and its ok."
2. **The function authenticates its caller** and never reads identity from the request body.
3. **Scope is link-only.** Paid-status tracking is in `TODOS.md`.
4. **Two data transforms are required.** Phone is persisted raw with dashes
   (`EditableTable.jsx:141`); Grow wants `0501234567`. `normalizeStudentName` returns *up
   to* two words and can return one, while Grow's Full Name field demands first and last,
   each 2+ characters.
5. **The popup blocker is a design input.** A prepared link sidesteps it, because the send
   click has nothing to await. Unprepared rows use the two-click path.
6. **A minted link belongs to the amount it was minted for.**
7. **Sandbox credentials until the round trip is proven.**

## Cross-Model Perspective

Codex cold read (office-hours) proposed the monthly "collection run"; the prepare-all half
was adopted, the paid-status outbox half stays in `TODOS.md`. It also challenged premise 2
into existence: hiding a secret behind an unauthenticated public endpoint moves the open
door rather than closing it.

Codex outside voice (eng review) found 14 issues, 4 of which corrected the review itself:
Make's operation accounting was understated 3x, appending the link would leave the dead
placeholder text visible, the single-settings-write plan still spread a stale snapshot,
and `amountOverride` being component-local silently breaks prepare-all. All four are folded
in below. Its recommendation to drop Make for Grow's direct API was considered and rejected
(see NOT in scope).

## Approaches Considered

### Approach A: Thin vertical slice
Minimal error handling, normalization inline in the component. **Rejected:** unreachable by
`deno test`, and the two known failures would ship unhandled.

### Approach B: Complete single-student flow, extended with batch preparation (chosen)
See Recommended Approach.

### Approach C: Let Grow deliver by SMS
**Rejected:** students get a bare provider SMS instead of the Hebrew message in the WhatsApp
thread they already use.

## Recommended Approach

**Approach B**, as amended by the engineering review. Eleven decisions:

1. **One new lib module, not two.** `src/lib/payments.js` holds phone normalization, full
   name validation, the Hebrew description builder, and the amount comparison, with one
   test file. Four new files became two.
2. **Service logic in `src/api/paymentLinkService.js`**, with `api/create-payment-link.js`
   as a thin Vercel adapter. Vercel requires the root `api/` folder, which `deno test`
   cannot reach; `src/api/` can, and `src/api/calendarApi.js` plus
   `tests/calendarApi.test.js` are the existing precedent. This makes all eight auth and
   failure paths testable with zero new tooling.
3. **Caller auth via one Google tokeninfo call**, checking the email against an
   `ALLOWED_EMAIL` env var, the audience against this app's Google client id, and expiry.
   Identity is read from Google's answer, never from the request body. Invisible to the
   teacher: the token already carries `email profile` scope (`useAuth.js:54`).
4. **Payment links live in their own localStorage store**, `vocalCalc:paymentLinks:<hash>`,
   keyed by `{month}:{student}`, written per link as it arrives. NOT in the settings blob.
   This supersedes an earlier decision to batch them into one settings write: that write
   still spread a settings snapshot captured before the batch began, wiping edits made
   during the ~15 seconds of preparing, and an interruption at student 34 lost all 34.
5. **Invalidation is amount-only.** A stored link is reused unless the amount changed.
   Accepted residual: correcting a name or phone after a link was minted leaves the stored
   link carrying the old value, which is cosmetic on the payment page while the amount
   charged stays correct.
6. **The adjusted amount is lifted out of `StudentRow` and persisted, keyed by
   `{month}:{student}`.** `amountOverride` is `useState` inside the row
   (`EditableTable.jsx:74`), so a table-level prepare-all button cannot see it and would
   mint links for calculated amounts, silently ignoring every manual adjustment.
   Persisting also stops a reload from destroying overrides, which under amount-only
   invalidation would re-mint every adjusted link. **The month key is required:**
   `customer_details` is keyed by student alone (`App.jsx:50`), so storing the override
   there would carry a one-off March adjustment into April and every month after,
   charging the wrong amount forever. An override belongs to one invoice, not to a
   student.
7. **Link placement order: `{link}` token, else the legacy `[קישור לתשלום]` placeholder,
   else append.** `SettingsPage.jsx:35` means a saved `default_message` wins over the
   built-in template, and any saved template carries that literal text rather than a
   token, so naive token substitution would silently send messages with no link. The
   placeholder exists to mark where the link goes, so the link replaces it.
   `SettingsPage.jsx:162` must list `{link}` alongside the existing four tokens.
8. **`HEBREW_MONTHS` is exported from `whatsapp.js`** rather than duplicated in
   `payments.js`.
9. **Prepare-all runs 6 requests concurrently** (~15s for 35 students). Every row updates
   independently the moment its own link lands.
10. **Make stays in the middle.** Grow's direct API was verified to exist but is not
    self-serve.
11. **A per-row "regenerate link" action.** Amount-only invalidation can otherwise hold a
    consumed, expired, or disabled link indefinitely with no way to force a new one.
12. **Every month-dependent operation reads `summary.month`, never the month input.**
    `CalculatorPage.jsx:75` passes `month={month}`, the input's live state, while
    `line 61` correctly shows `summary.month` for the data actually on screen. Change the
    month input without pressing Calculate and the rows stay on the old month while the
    prop moves to the new one. This is a **live bug in shipped code**: `EditableTable`
    hands that prop to `buildPaymentMessage` (`line 143`), so a student can already
    receive a message naming the wrong Hebrew month over the previous month's totals. The
    payment work compounds it, because the Grow description and the `{month}:{student}`
    keys for both the link store and the amount override would all inherit the wrong
    month, filing one month's money under another. Fix by passing `summary.month`
    everywhere the invoice month is meant. `handleDownload` (`line 32`) has the same
    staleness in the CSV filename, which is cosmetic and rides along with the fix.

Plus two UI corrections the review surfaced:

- **The row expands for detail editing whether or not a phone exists.** Today
  `EditableTable.jsx:232` only expands rows with a missing phone, so flagging a one-word
  name would give no way to fix it.
- **Grow's Notify URL is required** even though the callback is out of scope, and Grow
  retries at ~10, 20, and 30 minutes when nothing acknowledges. It points at a stub
  endpoint returning 200 so those retries stop.

## NOT in Scope

- **Paid-status tracking.** Grow's notify callback is server-to-server and cannot reach
  localStorage. Needs persistent state outside the browser. In `TODOS.md`.
- **Grow's direct API, dropping Make.** Verified to exist (`x-api-key`, User ID, Page Code,
  server-side only) and it would remove a middleman, its latency, and its operation budget.
  Rejected because Grow's docs require contacting support to issue credentials, with no
  knowable wait, while the Make path is already connected and half configured.
- **Idempotency for interrupted requests.** If Grow mints a link but the round trip times
  out, a retry mints a second one. Harmless here (only one link is ever delivered) but it
  clutters the Grow dashboard. In `TODOS.md`.
- **Pruning the link store.** ~105 entries a year against a 5MB budget. In `TODOS.md`.
- **React component tests.** `deno test` cannot render React; button states, batch
  progress, and the name flag stay hand-tested. The RTL/jsdom work is its own TODO with
  its own PR, deliberately.
- **Landing the 20-commit backlog.** This branch is 20 commits ahead of `main`, including
  the CSV wizard, Settings page, WhatsApp feature, and token-refresh fix. This feature
  cannot ship independently of them. Sequencing is a release decision, not a design one.
- **Registering Vercel preview origins with Google OAuth.** Preview deployments have
  different origins and will fail sign-in unless registered. Deployment config, not design.

## Failure Modes

| Codepath | Realistic failure | Test? | Error handling? | User sees |
|---|---|---|---|---|
| tokeninfo call | Google unreachable or throttled | yes | 503 from service | "Try again" on the button |
| tokeninfo call | Malformed response body | yes | treated as auth failure | "Sign in again" |
| token check | Expired token | yes | 401 | "Sign in again" |
| token check | Token from another Google app | yes | 403 | "Not authorized" |
| Make call | Timeout or 5xx | yes | surfaced, no partial write | Row marked failed, retryable |
| Make call | 200 with no link in body | yes | hard error | Row marked failed, never `undefined` |
| Make call | Returns a non-https string | yes | rejected before storage | Row marked failed |
| amount | Negative, zero, or non-finite | yes | rejected before the request | Row marked invalid |
| phone | Missing or malformed at the service layer | yes | rejected before the request | Row marked invalid |
| prepare-all | Interrupted at student 34 | yes | per-link writes already persisted | 34 rows still ready |
| send | Stored link, amount since changed | yes | signature mismatch re-mints | Correct amount sent |
| template | Saved message has neither token nor placeholder | yes | appended | Link present, at the end |

**Critical gaps (no test AND no error handling AND silent): 0.** Every silent-failure path
the review found (the dropped link, the ignored amount override, the lost batch) now has
both handling and a test requirement.

## Open Questions — resolved (T1)

- **Shekels or agorot?** Shekels, sent as-is. A live `487.50` round-trip landed on Grow's
  payment page as `"price":487.5` — no agorot conversion.
- **Response key name.** The Make scenario (Custom Webhook → Grow Create Payment Link →
  Webhook response) returns `{"status":1,"err":{},"data":{"paymentLinkProcessId",
  "paymentLinkProcessToken","url"}}`. The link is `data.url`.
- **Request payload.** The webhook expects `{customer_name, amount, phone, description}`.
  `phone` must be Grow's raw format (`normalizePhoneForGrow`, e.g. `0501234567`), and
  `description` is the Hebrew string from `buildGrowDescription` — confirmed to render
  correctly on Grow's page, month name included.
- **Getting the real response required two Make-side fixes**, not just filling in fields:
  the scenario had to be turned ON (an inactive scenario returns
  `"There is no scenario listening for this webhook"`, 410), and the trigger needed a
  Webhooks → "Webhook response" module as its last step — without one, Make always replies
  `"Accepted"` immediately and runs the rest of the scenario asynchronously, so the caller
  never sees the link.

## Success Criteria

- A sandbox link comes back and opens a payment page with the right amount and a Hebrew
  description naming the month.
- The link replaces `[קישור לתשלום]` in the message.
- A student stored as `050-1234567` succeeds.
- A one-word student is flagged before send, and can be fixed inline on a row that already
  has a phone.
- "Prepare all links" leaves failures marked per row, and prepared links survive a reload.
- An amount adjusted by hand is the amount the link is minted for, and that adjustment
  does NOT reappear the following month.
- Calculating August, then changing the month input to September without pressing
  Calculate, does not produce a September link, a September description, or a September
  message for August's totals.
- `deno test` covers phone normalization, name validation, amount comparison, and all eight
  service auth and failure paths.
- An unauthenticated `curl`, and a valid Google token from another account, are both
  rejected.

## Distribution Plan

Existing pipeline: push, Vercel builds and deploys. `/api/*` becomes a deployed function
alongside the static build. Local development of anything under `api/` needs `vercel dev`;
`npm run dev` does not serve those routes — and neither does `vite preview`.

**Env vars must be registered on the Vercel project itself (`vercel env add`), not just in
a local `.env.local` file.** `vercel dev` delegates the frontend to a `vite --port $PORT`
child process, which reads `.env.local` normally (so client-side vars like sign-in already
work from a local file) — but the separate function runtime for `/api/*` only receives env
vars that are registered on the linked Vercel project for the **Development** environment
specifically. A hand-edited `.env.local` with new vars is invisible to the function even
after a restart; `vercel env ls` will show them missing. Fix is `vercel env add <NAME>
development --value "..."` for each of `MAKE_WEBHOOK_URL`, `MAKE_API_KEY`, `ALLOWED_EMAIL`,
`VITE_GOOGLE_CLIENT_ID` (this project's `VITE_GOOGLE_CLIENT_ID` was already registered for
Production/Preview but not Development, which silently 403'd every local test until this
was found — confirmed by reproducing it directly and diffing `vercel env ls` before/after).
Production/Preview still need the same four vars added before the first real deploy.
